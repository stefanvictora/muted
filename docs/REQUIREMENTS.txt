Implementation plan for a local grayscale extension

HISTORICAL PLAN: This is the original pre-implementation plan, translated into
English. Later simplifications supersede parts of it, including per-domain
permissions, release requirements, and the original German-only interface.
See DEVELOPMENT.md, SECURITY.md, and VERIFICATION.md for the current behavior.

Date: October 24, 2026
Working name: Muted
Target: personal use on Windows in Microsoft Edge and Google Chrome
Original status: complete plan; no extension implemented or installed

1. Goal and agreed scope

Build a small, self-controlled Manifest V3 extension. It renders websites in
grayscale without third-party extension updates, external libraries, tracking,
or a network service of its own. Edge is the primary browser; Chrome is also
used, particularly for YouTube.

Confirmed product decisions:

- Two modes: "Everything gray except …" and "Only selected websites gray".
- Initial mode: "Everything gray except …", with an empty exception list.
- Initial setup requires deliberate approval of the necessary website access.
  Without approval, the interface shows the missing access; it must not silently
  switch to other permissions or another mode.
- Global on/off switch; grayscale always at 100 percent intensity.
- Global pause within each browser for 5, 15, or 30 minutes, with an option to
  end it early. No separate timers per website.
- Clicking the extension icon opens a compact German menu.
- An explicitly specified domain includes its subdomains.
- Settings and a deliberate manual off state survive restarts. A pause ends
  according to wall-clock time, including after sleep or restart.
- Edge and Chrome have separate settings and pauses.
- Local JSON export/import for the mode and domain lists.
- Normal HTTP/HTTPS websites; no local files or private windows.
- No support for browser UI, internal browser pages, extension stores, or
  built-in PDF viewers.
- Personal local installation; no store upload or automatic updater.

The technical decisions below specify how these requirements are to be met.
The name is a replaceable working name, not an additional product feature.

2. Security goal and its limits

The central goal is to remove a third-party publisher's update path: independent,
readable source code loaded locally as an unpacked extension, without update_url,
remote configuration, a downloader, or subsequently loaded code components.
Chromium's automatic update selection excludes unpacked installations. [1]

Installed files come from a reviewed release. Development, testing, and package
preparation never automatically write to the installed folder. A watcher,
automatic pull, or build inside the installation folder is not part of the system.

This does not prevent another local program with sufficient permissions from
modifying the files. A browser defect or a deliberately installed malicious local
change is also outside this protection. Hash manifests help with comparison;
if the files and manifest are in the same writable location, they do not provide
forgery-proof tamper protection.

Broad website permissions remain technically powerful in global mode. "Keep this
website in color" does not revoke browser permission. The reviewed page code
should only control the filter, not inspect page contents.

3. Technology and deliverables

- Manifest V3, standard chrome.* APIs, native JavaScript modules in the worker and UI.
- No framework, bundler, TypeScript build, or package manager for the runtime.
- Only bundled JS, CSS, HTML, and image files.
- A small classic, idempotent script for isolated page execution.
- Automated logic tests using Node's built-in test runner and local browser API
  doubles; Node is not required to use the extension.
- Browser checks in the actual stable versions of both browsers in use. Determine
  versions during implementation and record them in the verification report;
  do not invent version numbers in advance.
- Initial API baseline: Chromium 102; use methods that have been available for
  some time. Current Edge/Chrome versions are the acceptance targets. Do not fall
  back to unsafe APIs if a required capability is missing.

Planned package components:

  extension/manifest.json              Permissions and entry points
  extension/background.js              Events and central coordination
  extension/core/policy.js             Pure desired-state decision
  extension/core/domains.js            Domain normalization and matching
  extension/core/schema.js             State and import validation
  extension/services/state.js          Local storage and migration
  extension/services/permissions.js    Grants and permission removal
  extension/services/filter.js         Registration and existing tabs
  extension/services/pause.js          Deadline and alarm reconciliation
  extension/content/controller.js      Small isolated filter controller
  extension/content/filter.css         Grayscale rendering only
  extension/popup/                     Compact controls
  extension/options/                   Lists, mode, import, and export
  extension/assets/                    Bundled icons

Outside the installable package:

  tests/                              Logic and integration checks
  docs/                               Installation, security, and test matrix
  release-manifest.txt                Version, file list, and SHA-256 hashes
  CHANGELOG.txt                       Traceable changes

The module structure separates browser access from pure logic. No plugins,
generic script runners, or extension points for third-party code are introduced.

4. Permission model

Fixed API permissions:

  storage    Local settings and pause
  scripting  Register and apply/remove bundled filter files
  activeTab  Identify the current website after opening the menu, even before
             persistent permission for that website exists
  alarms     Timed pause despite a sleeping service worker

Optional host permissions:

  http://*/* and https://*/*

No mandatory broad host_permissions or static content_scripts for all pages.
Access is requested deliberately and scripts are then registered dynamically.
activeTab alone is insufficient for automatic filtering because it is temporary
and initiated by the user. [2]

No tabs, cookies, history, downloads, debugger, webRequest, proxy, nativeMessaging,
or unlimitedStorage permission. No file: patterns. Exclude Incognito/InPrivate
with "not_allowed" in the manifest. No externally_connectable,
web_accessible_resources, MAIN-world code, or sandboxed third-party code.

Global setup explains the access and requests broad optional hosts from an
explicit button click. Rejection remains possible. The resulting state is
"Setup: website access missing".

In selected mode, request access only to explicit domain rules. A saved rule is
not yet a browser permission. Rules without a grant show "Access required" and
must not silently gain persistent activation through temporary activeTab access.

Respect browser-side changes to website access. The extension never expands its
own grants automatically after permission loss. Even with an API grant, the actual
injection attempt is decisive; browser policies or protected targets may reject it.

5. Safe transitions between modes

Keep both lists independently:

  colorExceptions   Domains kept in color in global mode
  grayscaleSites    Domains turned gray in selected mode

Only the active mode's list affects the filter. Switching modes does not delete
the other list. Entries are not inverted or automatically reinterpreted.

Request permissions immediately inside the extension UI's click handler using
host patterns that were validated and prepared beforehand. No preceding await or
worker message round trip may lose the required user activation. The worker then
verifies the actual grant before committing. The browser may skip a new dialog
when access was previously approved; the guarantee is an explicit click, not a
new browser dialog on every request.

Selected to global:

1. Display the intended scope.
2. Request comprehensive website access directly from the user's click.
3. Save the mode and reconcile existing/new pages only on success.
4. Keep the previous state on rejection.

Global to selected:

1. Show the transition and block conflicting actions. Persist the transition
   state before starting side effects.
2. Remove global registration and clean up existing filters while permissions
   are still available.
3. Determine and remove the optional host grants that actually exist. Do not
   assume earlier narrow grants will remain. Remove only optional HTTP/HTTPS
   origin grants, not required fixed API permissions. Verify the access that
   actually remains afterward.
4. Save the intended selected mode; preserve both lists.
5. In a separate explicit "Allow selected websites" action, request only those
   specific hosts. A second click is intentional so the browser request reliably
   originates from user activation. [3]
6. Apply the filter only to matching pages that are actually permitted afterward.

If revocation fails, the UI must not claim that only the selected websites can
be read. Show the actual broader access and a way to retry cleanup. The filter
itself does not continue globally during the transition. A persisted transition
state allows resumption after worker termination with filter registration disabled.

Removing individual selected rules also requires checking for permissions no
longer needed. Overlapping rules, such as example.com and docs.example.com, must
not lead to false promises about remaining access. When in doubt, clean up and
request explicit permission for the remaining rules again instead of silently
retaining broad access.

Normal off and pause retain granted website permissions; switching to selected
websites deliberately reduces them. Isolated script contexts already created may
continue to exist until navigation despite cleanup and permission removal.
Deactivate classes/observers; fully removing old document contexts requires reload.

6. Domain rules and input

A domain d matches a host h exactly when h equals d or ends with a dot followed
by d. Thus reddit.com also matches old.reddit.com, but not notreddit.com or
reddit.com.example.org.

The UI suggests the actual current hostname and shows "including subdomains".
A broader domain must be explicitly selected or entered. Do not automatically
shorten docs.google.com to google.com or a hosted project to its platform domain.
Do not load an external public suffix list or guess a domain from its final two
name components.

Normalization and validation:

- Trim surrounding whitespace, lowercase, and remove a trailing DNS dot.
- Canonicalize internationalized names with the built-in URL parser; display the
  stored ASCII/Punycode form additionally if needed.
- Accept hostnames only: no paths, ports, credentials, query parameters, fragments,
  regular expressions, or user-entered wildcards.
- Check total DNS length and label limits; reject empty/invalid labels.
- Match IP addresses and localhost exactly when used as normal HTTP/HTTPS targets;
  never generate subdomain patterns for them.
- Deduplicate canonicalized rules and display them in a stable sort order.
- Never render input as HTML: use textContent and DOM methods, not innerHTML or
  document.write for rule text.
- Technical V1 limit: at most 200 rules in total. Show a clear error instead of
  silently truncating excessive input.

Overlapping entries within a list are allowed and marked as redundant. There is
no hidden priority order or contradictory rule within the same list. For example,
keeping google.com in color also keeps docs.google.com in color; a more precise
selection requires replacing the broad entry with the intended narrower entries.

7. State model and explicit priorities

Persist state in chrome.storage.local as a versioned object:

  schemaVersion        Integer, initially 1
  enabled              Boolean, default true
  mode                 global or selected, default global
  colorExceptions      List of normalized hosts, initially empty
  grayscaleSites       List of normalized hosts, initially empty
  pauseUntil           UTC timestamp in milliseconds or null
  permissionTransition Optional state for interrupted permission cleanup

Do not persist tab IDs, browsing lists, page contents, keystrokes, cookies, or full
URLs. Current tab URLs may be evaluated temporarily for decisions. Obtain actual
permissions from the browser rather than relying on a stale saved "granted" flag.

Decision for each document, in this order:

1. Protected/unsupported target -> do not inject; show the appropriate status.
2. Setup or permission cleanup incomplete -> no filter.
3. enabled is false -> color, reason "Off".
4. pauseUntil is in the future -> color, reason "Paused until …".
5. Global: matching color exception -> color; otherwise grayscale is desired.
6. Selected: matching selected rule -> grayscale desired; otherwise color.
7. Grayscale desired but required access missing -> no filter, reason
   "Website access required"; no misleading success message.
8. After successful application -> "Grayscale active". Keep errors visible without
   logging third-party page contents or full URLs.

The UI distinguishes desired state, missing permissions, and confirmed application.
It must not display success for an operation that failed.

Additional transition rules:

- Manually turning off ends an active pause and removes its alarm.
- Manually turning on immediately applies the rules; an old pause does not return.
- Pause is available only while the main switch is on.
- Clicking pause again sets the deadline to now plus the chosen duration; do not
  add remaining durations in ways that are hard to understand.
- "End pause" clears the deadline to null and applies current rules.
- Rules and mode may change during a pause; the filter stays off until it ends,
  then the latest settings apply.
- On a corrupt or unknown newer schema, do not automatically reset to global
  access. Enter an error state without new injection and provide a recoverable UI.

8. Filter-control architecture

The service worker is the central writer. UI commands reach it through typed,
strictly validated internal messages. Only the extension's own popup/options pages
may request settings changes: validate sender ID, origin, path, and message schema.
No arbitrary function names, script text, or file paths in messages.

Process state changes serially and assign a revision. Save first, then reconcile
the effective state. Stale asynchronous results must not overwrite newer settings.
Repeated reconciliation must produce the same final state.

Reconcile on installation/update, browser startup, worker restart, UI actions,
alarms, and relevant permission changes. Register event listeners synchronously
when the worker loads; handlers wait for initialization. Global JavaScript variables
are a cache, not persistent truth.

For new documents:

- Dynamic registration with fixed extension-owned IDs, document_start, ISOLATED.
- Global: HTTP/HTTPS patterns with excludeMatches for color exceptions.
- Selected: only specific domain patterns with current grants.
- No active filter registration for new documents while off, paused, or in a
  permission transition.
- Registration may persist across sessions compatibly in both browsers; reconcile
  it against state and permissions at startup anyway. [4]
- Registration IDs must not begin with an underscore. Updates provide all intended
  properties, including empty exclusion lists, so old excludeMatches do not remain
  accidentally.

For existing tabs:

- Determine eligible targets and reconcile in bounded batches.
- Apply or deactivate the bundled CSS file and idempotent controller.
- A target may navigate or close during the operation: isolate failures, with no
  global abort or unlimited retry loop.
- On URL/document changes, do not apply stale decisions from a previous tab state.
  The controller checks that its current host still matches the expected target
  or supplied rules; otherwise reconciliation is required.

Page code:

- Top-level document only; no allFrames or expansion to about:/data:.
- Small IIFE with one instance in the isolated execution context, so repeated
  injection causes no global const collisions, duplicate listeners, or observers.
- No chrome.storage or network access, and no inspection of page contents.
- Add/remove a uniquely named extension-owned class on the html element.
- Handle early startup without an html element safely: wait briefly for the root
  rather than permanently observing the entire page tree.
- If page scripts overwrite the class, use at most one narrowly scoped observer
  of the root's class attribute, only while the filter is active. Do not observe
  text, form values, or arbitrary content changes.
- On deactivation, stop local observers first, then remove the extension's class
  and temporary resources. A still-active observer must not reactivate the filter.

Bind CSS to the extension's own class so remaining declaratively injected CSS has
no effect after deactivation. unregisterContentScripts alone does not remove CSS
or JS already injected. Also remove programmatically injected CSS using the same
file details and origin. [4] Do not overwrite/delete third-party style attributes
or stylesheets.

After external permission revocation, cleanup of an open document may fail.
Deactivate existing controllers where still reachable; otherwise clearly show
"Reload the page". Do not promise that an existing effect can always be removed
immediately after permission loss.

9. Pause and recovery

Use a named chrome.alarms alarm plus a persisted pauseUntil deadline. Do not use
setInterval/setTimeout in the service worker as the clock.

On every initialization and alarm:

- Deadline in the future: ensure the correct alarm exists; keep the filter off.
- Deadline expired: clear the deadline, remove the alarm, and apply the latest state.
- No deadline: remove any stale alarm.

The popup may update its displayed remaining time locally. It does not decide
whether the filter is actually re-enabled.

Do not depend on persistAcrossSessions, an alarm option introduced in newer Chrome
versions; explicitly restore alarms. Alarms do not wake a sleeping computer and
may fire late. On resumption, the persisted absolute deadline applies. System clock
changes alter the remaining duration accordingly. [5]

10. User interface

German popup, usable with a keyboard:

- Current hostname, without an unnecessary full URL.
- Clear status: grayscale, exception, not selected, paused, off, access required,
  or not supported.
- Main on/off switch; off remains in effect until explicitly turned on.
- Appropriate action for the current website: "Keep in color" or "Make gray",
  with a preview of the domain and its subdomains.
- Pause for 5/15/30 minutes, visible end time, and "End pause".
- Link to the extension's own local settings page.

Settings page:

- Mode selection with a clear explanation of website access.
- Both domain lists, with the currently active list identified.
- Add/remove controls, validation errors, and overlapping rules.
- Display actual optional website grants and targeted repair actions.
- JSON export/import with preview.
- Local version display and brief installation/update information.

Badge/tooltip: ON, OFF, paused, or action required. Do not rely on color alone.
Provide focus indicators, labels, screen-reader names, and sufficient contrast.
No automatically opened external tabs, donation links, or review links.

11. Local export and import

Export only formatVersion, mode, colorExceptions, and grayscaleSites. Do not
include enabled, pause, browser permissions, tab data, or browser identification.
The current on/off setting and active pause remain unchanged during import;
imported rules follow the usual priorities.

After preview, import completely replaces the mode and both lists. No silent
merging. Allow exporting the current state before confirmation. Never import
browser permissions from a file or request them without a separate user click.

Technical limits and validation:

- At most 64 KiB of file content and 200 rules in total.
- JSON.parse only; never eval or executable configuration.
- Exact allowed keys and types; reject unknown format versions.
- No recursive merges or acceptance of __proto__, constructor, or prototype keys;
  construct new objects from validated fields.
- Apply the same domain validation as for manual input.
- Validate the entire file, show a preview, then apply all changes together.
- An invalid file changes no state.
- A global import without broad access remains a visible prepared request; the
  previous effective mode must not silently gain broader access. Completion uses
  the same deliberate permission/mode transition as the UI.

Export a locally generated JSON file through a download link/Blob, then revoke
the object URL; no downloads permission. If a browser CSP adjustment is needed,
allow only the specific local capability required, not network sources broadly.

12. Additional security measures

- Restrict chrome.storage.local to TRUSTED_CONTEXTS; page code does not need access
  to rules or settings. [6] Wait for this initialization before new registrations
  or state handlers. Check availability; handle failures visibly rather than
  silently falling back to a less restrictive storage model.
- Strict CSP for extension pages and the worker: generally default-src 'none',
  script-src 'self', style-src 'self', img-src 'self', connect-src 'none',
  object-src 'none', frame-src 'none', base-uri 'none', form-action 'none'.
  No inline scripts, inline event handlers, external fonts, or CDNs.
- Verify the actual policy in the package and both browsers. It is additional
  protection for extension contexts, not a global firewall for DOM changes on
  websites. [7]
- No fetch/XHR/WebSocket/sendBeacon, WebRTC, or other outgoing functions; no remote
  assets, imported scripts, or dynamic code evaluation.
- No custom workarounds that bypass browser security mechanisms.
- Keep diagnostics local and minimal: error code, component, possibly a temporary
  tab ID; no browsing history or full URLs in persistent logs.
- Version schema migrations explicitly. Failed migrations must not silently
  overwrite settings.
- Fully review the manifest and runtime files before each release. Pattern searches
  are an additional aid, not a substitute for reading code and testing behavior.

13. Rendering limitations and quality goals

The filter affects the rendered page. A root-element filter can override existing
CSS filters, alter stacking contexts, and affect fixed/sticky elements on some
pages. Turning off must restore the page's original CSS; do not permanently change
third-party styles.

Filtering the outer document should also cover normal embedded content. Do not
preemptively inject additional code into third-party frames. Test fullscreen,
Picture-in-Picture, embedded PDFs, and unusual video rendering separately. Do not
promise to filter browser Picture-in-Picture or every protected view.

For YouTube fullscreen, first evaluate a narrowly scoped CSS solution in the
already permitted top-level document. Do not automatically expand to allFrames
or MAIN world as a fix. Document special cases that cannot be safely supported
as limitations.

Aim to filter as early as possible from document_start. Do not claim completely
flicker-free rendering on first consent, permission changes, browser startup, or
resumption after an alarm. Check visible delays in both browsers.

14. Test strategy and acceptance criteria

Automated logic tests:

- Exact domain/subdomain matching and false suffixes; uppercase, trailing dot,
  IDN, IPv4/IPv6, invalid hosts, and size limits.
- Both modes with separate lists and empty lists.
- All state priorities, including off, pause, exceptions, and missing permissions;
  an old alarm must not turn a disabled filter on.
- Pauses before/after the deadline, repeated pauses, and clock changes.
- Imports with unknown keys/versions, HTML-like text, prototype keys, and oversized
  files; atomic rejection and exact export fields.
- Registration patterns match the rules; no expansion to file:, allFrames,
  or MAIN world.

Integration checks with simulated browser APIs:

- Rapid toggle sequences, delayed APIs, and worker reinitialization.
- Grants, rejection, revocation, and overlapping host permissions.
- Interrupted global-to-selected transition and failed permission removal.
- Alarm missing after restart; pause expired while browsers were closed.
- Tab closes/navigates during a batch.
- Duplicate injection and repeated deactivation remain idempotent.
- Manipulated internal messages have no effect.

Manual browser acceptance in BOTH Edge and Chrome:

1. Load locally; the browser shows an unpacked installation and expected API
   permissions. Global access exists only after explicit approval.
2. Global startup filters new and already open normal pages; color exceptions
   also cover matching subdomains.
3. Selected mode filters only selected and permitted domains; broad permissions
   are actually removed after a successful mode transition.
4. Popup status matches actual rendering; failures do not suggest successful
   protection or filtering.
5. Test Reddit including old.reddit.com, YouTube including SPA navigation and
   fullscreen, and at least one page with sticky elements and a cross-origin frame.
6. Off/pause/removing a rule affects existing and new tabs; no active observers
   or returning filters remain.
7. Close the browser, terminate the worker, and test sleep/wake with expired and
   active pauses. Also test with worker DevTools closed, since they can affect
   normal worker suspension.
8. Private windows, local files, internal pages, stores, and PDF viewers remain
   outside the promised scope; explain this in the UI without excessive errors.
9. Import/export between Chrome and Edge; no automatic synchronization or transfer
   of pauses or permissions.
10. Inspect extension-context network activity on a local test page and during all
    UI actions: no external requests caused by the extension. Treat normal traffic
    from a visited website separately.
11. The live package matches the release file list and hashes.

Release only when core behavior, permission transitions, pause/recovery, and
security checks pass in both browsers. Mark unavailable browser checks as pending;
never invent passing results. Document specific rendering edge cases; do not
relabel a core-flow defect as a mere limitation.

15. Implementation in verifiable steps

Phase 1: Foundation and pure logic
  Manifest design, state/import schema, domain rules, and desired-state function;
  relevant logic tests and permission-requirement review.

Phase 2: Filter and coordination
  Small isolated controller, CSS, dynamic registration, cleanup of existing tabs,
  and serialized worker state processing.

Phase 3: Permissions and both modes
  Initial setup, optional hosts, modes with independent lists, safe permission
  reduction, browser-side changes, and recovery after interruption.

Phase 4: Pause and interface
  Persistent deadline with alarm reconciliation, popup, list management, clear
  status reasons, and keyboard accessibility.

Phase 5: Import and export
  Local files, strict validation, preview, atomic application, and deliberate
  approval of any required permission changes.

Phase 6: Audit and browser acceptance
  Complete code/manifest review, automated tests, actual Edge/Chrome test matrix,
  network checks, and fixes for discovered defects.

Phase 7: Local release
  Verification report, installation guide, changelog, release archive, file hashes,
  and documented rollback. No automatic installation.

This plan itself does not perform development or installation.

16. Installation and controlled updates

Planned local separation:

  Working source:    dedicated development folder
  Release archives:  versioned, unchanged snapshots outside the runtime
  Installation:      a stable folder chosen by the user, <installation-folder>

The installation folder contains only the approved extension directory. This is
a proposed future path, not a folder created by the plan. Both browsers may load
the same stable path; their settings remain separate despite sharing code files.
Browser installation is performed and checked separately. [8][9]

Initial installation:

1. Verify the approved archive/file hashes and place the runtime in the stable folder.
2. Edge: open edge://extensions, enable Developer mode, choose "Load unpacked",
   and select the folder containing manifest.json.
3. Chrome: follow the same process at chrome://extensions.
4. Pin the icon, open local setup, and deliberately accept global website access;
   initially there are no color exceptions.
5. Check browser status, a test page, and basic functions. Disable earlier grayscale
   extensions during acceptance testing so filters do not overlap.

Manual update:

1. Review changes and test evidence; create a new release with a hash manifest.
2. Back up existing files unchanged; export settings from each browser.
3. Temporarily disable the extension in both browsers.
4. Deliberately replace the entire installed file set with the verified new set;
   leave no obsolete files. This is not an automatic process.
5. Keep the path, reload/enable in both browsers, and verify ID, schema, and
   permissions. New documents or reloaded affected tabs ensure no old injected
   script instance remains active.
6. Perform a short acceptance check and verify state/lists in both browsers.

Depending on the context, a modified local file may take effect as soon as an
extension page is reopened. Do not claim "Reload" is the only security boundary.
The controlled replacement of files is what matters.

Rollback:

Disable both installations, restore the backed-up file set at the same path,
check state-schema compatibility, and use the previous export if necessary.
Then reload the extension and affected tabs. Old software must not silently
overwrite an unknown newer schema. Uninstalling may lose local settings;
export them first.

17. Planned final handoff

- Readable source and a clearly bounded installable directory.
- Versioned release archive with its own file list and SHA-256 hashes.
- Short German installation, update, and rollback instructions for both browsers
  (the language specified in the original plan).
- Verification report with actually tested browser versions and limitations.
- Security description: specific permissions, no third-party updates, no data
  transmission in the reviewed code, and remaining local trust boundaries.
